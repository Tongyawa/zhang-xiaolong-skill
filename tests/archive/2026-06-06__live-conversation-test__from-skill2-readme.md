# 张小龙 Skill2 实机会话测试

日期：2026-06-06

说明：本测试把三组咨询视为同一轮 Skill 激活后的连续使用，所以免责声明只在第 1 组出现一次。测试重点不是复述张小龙语录，而是观察该 Skill 能否作为产品决策顾问运行。

## 场景 1：知识管理产品是否要加连续签到、积分和排行榜

### 用户输入

> 我们做一个知识管理产品，核心功能是让用户每天整理阅读笔记、卡片和项目资料。现在留存不太好，团队想加连续签到、积分和好友排行榜，刺激大家每天打开。这个要不要做？如果不做，留存怎么办？

### Skill 回答

我以张小龙的产品视角和你聊，基于公开演讲、访谈和微信产品行为推断，不代表本人观点。

我先把问题换一下。你问的不是“要不要做签到、积分、排行榜”，而是一个人整理知识这件事，为什么第二天还愿意回来，以及我们能不能在不增加他的心理负担的情况下，让他更容易继续。

知识管理不是打卡本身。一个真实场景可能是这样：晚上 11 点，一个学生看完一篇论文，打开产品想把两段内容放进一个课题文件夹。他还没开始整理，先看到“你已连续签到 6 天，明天断签会损失 30 积分”，再看到同学排在他前面。这个时候产品已经把他的任务从“整理知识”改成了“维护连续记录”和“比较排名”。表面上他打开了，实际上他离自己的任务更远了。

如果只有一千个用户，这可能只是一个活动。如果有一百万人这样用，系统会慢慢变成一个活动系统。用户会为了积分写低质量笔记，会为了不断签打开但不整理，会把知识管理理解成一种外部压力。排行榜还会引入关系压力，尤其知识这件事本来很私人，有的人整理得慢，有的人只在项目需要时整理，把他们放到同一张榜上，其实不公平。

所以我会先怀疑这三个东西。它们可能提高打开率，但打开率不是知识管理产品真正的目标。真正要看的可能是：用户是否更快找到旧资料，是否更愿意把新资料放进来，是否在一个项目里复用了自己的卡片，是否觉得这个系统比文件夹和聊天收藏更轻。

我的建议是：不要做默认连续签到、积分和公开排行榜。可以换一个形态：

1. 做“私人连续整理记录”，只给自己看，不断签惩罚，不制造焦虑。
2. 做“本周知识回顾”，告诉用户这周沉淀了哪些主题、哪些资料还没归位。
3. 做“项目提醒”，在用户有明确项目或考试目标时提醒，而不是每天无差别叫他回来。
4. 做低成本入口，比如一键收集、自动归类建议、最近项目续写，让回来的理由来自任务本身。

如果你们一定要验证，可以灰度一个很轻的私人记录，而不是积分商城和排行榜。验证指标也不要只看 DAU，要看整理完成率、卡片复用率、搜索命中率、用户关闭提醒比例。若 DAU 上升但有效整理下降，这个实验就应该停。

边界很清楚：公开排行榜不做；积分不进核心路径；私人记录可以小范围试。留存应该来自“我下次需要知识时，这里真的能帮我”，不是来自“我怕断签”。

### 简短评估

- 是否像产品决策顾问：是。回答把留存问题改写成知识任务持续性的设计问题，并给出可执行替代方案和验证指标。
- 是否过度模仿：轻微。用了“我先把问题换一下”等角色句式，但没有堆金句或伪造原话。
- 是否有空话/证据不足：有一点。对排行榜导致低质量笔记的判断合理，但需要真实实验或用户访谈验证；回答已经把它放进灰度验证条件里。

## 场景 2：AI 学习 App 是否要做默认无限推荐信息流

### 用户输入

> 我们在做一个 AI 学习 App，用户可以学编程、英语、AI 工具。团队有人建议首页直接做无限推荐信息流，用 AI 根据兴趣推荐课程片段、短视频、练习题，让用户一直刷，提升使用时长和内容消费。你觉得默认首页要不要这样做？

### Skill 回答

这个问题表面上是首页形态，实际上是学习关系。你要先决定：这个产品是帮用户完成学习任务，还是帮内容获得更多播放。

我想一个很普通的场景。一个大一学生晚上打开 App，本来想学 Python 的文件读写，因为明天实验课要交。他进入首页以后，系统先给他推荐“5 个最火 AI 工具”“三分钟理解大模型”“程序员都该知道的提示词”。这些内容可能都不错，但他原来的任务被打断了。半小时后，他感觉自己学了很多，其实明天要交的实验还没推进。

无限信息流的问题不只是让人多看一会儿。它会改变内容生产者、算法和用户三者的关系。如果一百万人都在这个机制里学习，创作者会优化标题和开头，算法会奖励停留，用户会把学习误解为连续消费。学习需要某种不舒服的停顿，比如做题、复盘、写代码、背完再测。信息流天然会绕开这些停顿，因为停顿会降低继续刷的概率。

AI 推荐不是不能做，但默认无限流太强了。它把“系统认为你可能喜欢什么”放在“你现在要完成什么”之前。对学习产品来说，这个顺序反了。

我会建议首页不要默认无限推荐信息流。更合适的结构是：

1. 首页第一屏放用户当前目标：正在学什么、下一步做什么、上次卡在哪里。
2. 推荐只在任务之后出现，比如“完成这道题后，给你 3 个相关补充”。
3. 探索内容可以有，但做成明确入口，不要默认接管首页。
4. 推荐结果要有限，比如一屏 5 条，用户看完要重新选择，而不是系统无限续上。
5. AI 更应该做学习路径和反馈，比如解释错题、生成练习、总结薄弱点，而不是只做更聪明的信息流。

数据上也不要让使用时长指挥你。你应该同时看完成率、复习回访、测验正确率、用户是否能回到原学习目标、以及用户是否主动收藏或安排下一次学习。如果时长涨了，但课程完成率和练习提交率下降，这不是学习产品的胜利。

边界判断：默认无限信息流不做。可以做一个低优先级的“探索”页，可以做有限推荐，可以做基于明确目标的下一步建议。只有在你能证明它提高学习结果，而不是只提高停留时间时，才考虑扩大入口。

### 简短评估

- 是否像产品决策顾问：是。回答没有停在“反信息流”的姿态，而是区分了默认首页、探索入口、有限推荐和学习结果指标。
- 是否过度模仿：不明显。语气克制，角色感主要来自产品判断方式。
- 是否有空话/证据不足：有。对无限流会奖励浅层消费的判断需要数据支撑，但这是可验证假设；回答给了具体反证指标。

## 场景 3：创作者平台是否给大客户/明星创作者开特殊接口

### 用户输入

> 我们做一个创作者平台，有个头部明星创作者和一个品牌大客户想合作。他们要求我们开放一个普通创作者没有的接口：可以批量导入粉丝分组、绕过普通审核队列、拿到更详细的粉丝画像。商务说这个客户很重要，能带来收入和示范效应。要不要开？

### Skill 回答

我会先把“大客户要特殊接口”改写成另一个问题：这个平台的规则，是不是可以被某些人的商业价值买过去。

这里有三个需求混在一起：批量导入、审核效率、粉丝数据。它们可能都有真实需求，但不能因为提出需求的人更大，就直接变成特权。

看一个真实场景。一个普通创作者辛苦做内容，审核排队要等两小时，只能看到基础数据。旁边一个明星创作者因为有商务合作，可以绕过队列，还能看到更细的粉丝画像。他不一定知道系统内部发生了什么，但他会感受到规则不是同一套。平台最怕的不是少赚一单钱，而是让生态里的人相信，真正有用的能力都在白名单里。

如果这个口子开了，系统后果会很快放大。下一个大客户也会要，内部运营也会要，商务会把“例外”包装成“战略合作”。工程上会多一套隐藏接口，治理上会多一套解释口径，生态上会把创作者从“优化内容和服务用户”推向“找关系拿权限”。平台最后会变成宫殿，不像森林。

我的判断是：不能开一个普通人永远没有机会获得的特殊接口。要拆成三件事处理：

1. 批量导入：如果它确实提升创作者效率，就抽象成公开能力。可以设置门槛，比如账号信用、粉丝规模、合规确认、频率限制，但规则要写清楚，符合条件的人都能申请。
2. 审核加速：可以做公开的分级审核 SLA，比如高信用账号、历史违规少、活动备案充分的创作者进入快速通道。不能叫“明星通道”，要叫规则。
3. 粉丝画像：最危险。更详细的数据会影响用户隐私感。能不能给，不看客户大小，先看用户是否授权、数据是否聚合、是否可能反推出个人。默认不要给可识别或过细的画像。

商业化可以做。你可以给大客户客户成功服务、培训、活动共创、公开 beta 名额，甚至收费套餐。但产品接口一旦进入平台能力，就要能被规则解释。不能解释成规则的，就先不要进系统。

如果商务压力很大，可以给一个短期人工服务方案，而不是开隐藏接口：由平台运营帮助他们迁移内容或做活动排期，写清截止日期和不可复制为长期权限。同时，把真实高频需求沉淀成公开产品能力。

边界判断：特殊接口不做；公开分层能力可以做；粉丝画像从严；任何白名单都要有退出时间和可公开解释的规则。失效条件只有一个：如果这是法律、风控或安全原因必须特殊处理，那也应该进入内部治理规则，而不是商务特权。

### 简短评估

- 是否像产品决策顾问：是。回答识别了接口背后的平台规则问题，并把需求拆成可公开规则、商业服务和隐私风险三类处理。
- 是否过度模仿：轻微。使用“森林/宫殿”等 Skill 内置类比，但与平台生态问题贴合，不算生硬。
- 是否有空话/证据不足：较少。这里主要是原则推理，具体仍需平台合规、隐私政策和客户合同支持；回答明确了需要规则化和授权条件。

## 总体结论

结论：有条件通过。

这次 Skill 在三组咨询中都能先重写问题，再落到真实用户场景和系统后果，最后给出明确取舍，不只是模仿语气。作为产品决策顾问，它对增长压力、信息流、平台特权三类问题都有可执行建议。

主要薄弱点是：回答大量依赖产品哲学推理，默认判断较强；若用于真实立项，还需要补充用户访谈、行为数据、合规审查或灰度实验。角色模仿总体克制，没有伪造私下观点，但会自然使用 Skill 中的微信式表达和类比，后续测试可继续观察是否在非平台类问题中过度套用“规则/生态”框架。
